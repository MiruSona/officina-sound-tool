# SFX 엔진 재조사 — rfxgen `.rfx` 포맷 분석 + 대안 조사

> 대상: `Docs/Research/2026-08-19-사운드툴조사.md`의 SFX 추천(pyfxr) 후속 조사
> 조사일: 2026-08-20
> 범위: **SFX만** (BGM은 이미 확정, 이번 조사 대상 아님)

---

## 결론 (최종 추천)

**1순위: rfxgen을 그대로 쓴다.** `.rfx` 파일은 24개 필드짜리 아주 단순한 고정 바이너리 구조(104바이트, 헤더 8 + 파라미터 96)라서 Python `struct` 모듈만으로 직접 써낼 수 있다는 걸 소스 코드로 확인했다. Python에서 파라미터를 `.rfx` 바이트로 패킹 → `rfxgen --input x.rfx --output x.wav` 서브프로세스 호출, 이 두 단계만으로 완전 자동화가 된다. rfxgen은 2026-08-13에도 커밋이 있을 만큼 활발하고, 공식 Windows x64 바이너리(v5.0, 2025-11)도 제공한다. **pyfxr을 1순위로 쓸 이유가 이제 없다.**

**2순위(장기 안전판): 언젠가 외부 실행파일 의존을 없애고 싶으면 rfxgen의 소리 생성 알고리즘(`GenerateWave`, 약 310줄)을 Python으로 직접 포팅한다.** 이 알고리즘은 raylib/raygui 같은 외부 의존성이 전혀 없는 순수 C 코드(zlib 라이선스라 포팅도 허용)라서, 이식 난이도가 낮다. 포팅하면 Python 표준 `wave` 모듈만으로 외부 프로그램·컴파일러 없이 SFX를 만들 수 있다. 지금 당장 할 필요는 없지만 "이 알고리즘을 언제든 우리 것으로 만들 수 있다"는 사실 자체가 유지보수 중단 리스크를 크게 낮춘다.

**pyfxr 유지보수 중단은 심각한 리스크가 아니지만, 이제는 굳이 감수할 이유도 없다.** pyfxr 코어는 Cython 확장이라 소스 빌드에 컴파일러가 필요하고(현재 PyPI wheel은 Python 3.13까지만 제공, 3.14 wheel 없음), 최근 커밋도 2025-07이 마지막이다. rfxgen이 이미 더 활발하고, 포맷도 검증됐고, 파라미터 세밀도도 pyfxr과 동일(같은 sfxr 계열 필드)하므로 pyfxr을 쓸 이유가 사라졌다.

## 1. `.rfx` 포맷 분석

### 조사 방법
`raysan5/rfxgen` 저장소의 `src/rfxgen.c`(1465줄)와 `src/rfxgen.h`(1011줄, 소리 생성 로직이 담긴 헤더 온리 라이브러리)를 GitHub API로 직접 내려받아 전문을 읽었다.

### 결론: 포맷이 완전히 명확하고, 코드로 100% 생성 가능

`rfxgen.h`의 `SaveWaveParams()` 함수 주석에 파일 구조가 그대로 적혀 있다.

```
// Fx Sound File Structure (.rfx)
// ------------------------------------------------------
// Offset | Size  | Type       | Description
// ------------------------------------------------------
// 0      | 4     | char       | Signature: "rFX "
// 4      | 2     | short      | Version: 200
// 6      | 2     | short      | Data length: 96 bytes
// 8      | 96    | WaveParams | Wave parameters
// ------------------------------------------------------
```

총 104바이트. 헤더 8바이트 + `WaveParams` 구조체 96바이트. `LoadWaveParams()`도 이 순서 그대로 `fread`하고, 시그니처("rFX ")·버전(200)·길이(96) 세 가지만 검증한다. 복잡한 압축이나 가변 길이 필드가 전혀 없는 완전 고정 폭 바이너리다.

`WaveParams` 구조체 전체(`rfxgen.h` 79~124줄, 필드 순서 그대로):

| 순서 | 필드명 | C 타입 | 의미 |
| --- | --- | --- | --- |
| 1 | `randSeed` | int | 생성용 랜덤 시드 |
| 2 | `waveTypeValue` | int | 파형(사각/톱니/사인/노이즈) |
| 3 | `attackTimeValue` | float | 어택 시간 |
| 4 | `sustainTimeValue` | float | 서스테인 시간 |
| 5 | `sustainPunchValue` | float | 서스테인 펀치 |
| 6 | `decayTimeValue` | float | 디케이 시간 |
| 7 | `startFrequencyValue` | float | 시작 주파수 |
| 8 | `minFrequencyValue` | float | 최소 주파수(슬라이드 하한) |
| 9 | `slideValue` | float | 주파수 슬라이드 |
| 10 | `deltaSlideValue` | float | 슬라이드 가속도 |
| 11 | `vibratoDepthValue` | float | 비브라토 깊이 |
| 12 | `vibratoSpeedValue` | float | 비브라토 속도 |
| 13 | `changeAmountValue` | float | 음정 변화량(아르페지오) |
| 14 | `changeSpeedValue` | float | 음정 변화 속도 |
| 15 | `squareDutyValue` | float | 사각파 듀티비 |
| 16 | `dutySweepValue` | float | 듀티비 스윕 |
| 17 | `repeatSpeedValue` | float | 반복 속도 |
| 18 | `phaserOffsetValue` | float | 페이저 오프셋 |
| 19 | `phaserSweepValue` | float | 페이저 스윕 |
| 20 | `lpfCutoffValue` | float | 로우패스 컷오프 |
| 21 | `lpfCutoffSweepValue` | float | 로우패스 컷오프 스윕 |
| 22 | `lpfResonanceValue` | float | 로우패스 레조넌스 |
| 23 | `hpfCutoffValue` | float | 하이패스 컷오프 |
| 24 | `hpfCutoffSweepValue` | float | 하이패스 컷오프 스윕 |

int 2개(8바이트) + float 22개(88바이트) = 96바이트. 전부 4바이트 정렬이라 패딩 문제도 없다. 즉 Python에서 `struct.pack('<4sHH2i22f', b'rFX ', 200, 96, *params)` 한 줄로 `.rfx` 파일 전체를 만들 수 있다는 뜻이다(리틀 엔디안은 x64 raylib 빌드 관례상 확실).

이 구조는 **10년 가까이 안 바뀌었다.** `rfxgen.c` 상단 버전 이력에 "0.95 (14-Sep-2016) Reviewed comments and .rfx format"이라고 적혀 있고, 이후 v5.0(2025-11)까지 버전 번호(200)도 필드 목록도 그대로다. 포맷이 바뀔 걱정은 거의 없다고 봐도 된다.

### CLI로 `.rfx → .wav` 변환 지원 여부: 지원함, 확인 완료

`rfxgen.c`의 `ProcessCommandLine()` 함수를 그대로 읽었다. `-i/--input`으로 `.rfx`를 받아 `-o/--output`으로 `.wav`(그 외 `.qoa`, `.raw`, `.h`도 가능)를 만든다. 실제 사용 예시(공식 도움말 문구 그대로):

```
rfxgen --input sound.rfx --output jump.wav
rfxgen --input sound.rfx --output jump.raw --format 22050,16,2
```

`--format <sample_rate>,<sample_size>,<channels>`로 샘플레이트(22050/44100), 비트(8/16/32), 채널(1/2)까지 지정 가능. GUI를 전혀 띄우지 않고 순수 커맨드라인만으로 끝난다(내부적으로 `PLATFORM_DESKTOP`이면 인자가 있을 때 GUI 없이 바로 처리하고 종료).

추가로 `-g/--generate <preset>`으로 `coin, laser, explosion, powerup, hit, jump, blip` 7개 프리셋을 `.rfx` 파일 없이 바로 생성하는 기능도 있다(다만 프리셋은 정해진 종류만 가능해서, 세밀한 파라미터 제어가 필요하면 결국 `.rfx`를 직접 만들어야 한다).

### 부가 확인: 소리 생성 알고리즘 자체도 이식하기 쉽다

`rfxgen.h`는 `#define RFXGEN_IMPLEMENTATION` 방식의 헤더 온리 라이브러리로, **raylib이나 raygui에 전혀 의존하지 않는다.** 포함하는 헤더는 `stdlib.h, stdio.h, string.h, math.h, time.h`뿐이다(2022년 10월에 별도 개발자가 "헤더 온리 라이브러리로 포팅"한 결과). 핵심 함수 `GenerateWave()`는 310줄짜리, 샘플 단위로 도는 상태 기반 루프(페이즈/엔벨로프/필터 상태를 유지하며 한 샘플씩 계산)라서 Python으로 그대로 옮기기 어렵지 않다. 라이선스는 zlib/libpng — 상업적 사용, 수정, 재배포 모두 허용(원저작자 표기만 유지).

### 확인 못한 것
- `.rfx`의 리틀 엔디안 여부를 헤더 주석에서 명시적으로 못 찾았다. raylib/rfxgen이 x64 데스크톱(Windows/Linux/macOS) 대상이고 x64는 전부 리틀 엔디안이라 사실상 문제 없지만, 100% 명문화된 문서 근거는 아니다.
- `.rfx` 파일을 Python으로 실제로 만들어서 rfxgen에 넣어보는 검증(실물 테스트)은 하지 않았다. 이번 조사는 소스 코드 분석까지만 했고, 코드 작성·실행은 범위 밖이라 하지 않았다.

### 대안별 판단 근거

- **jsfxr(`sfxr-to-wav`)이 사실 가장 "요구사항에 글자 그대로 맞는" 도구다.** 이미 JSON을 stdin으로 받아 wav를 뱉는 CLI가 존재해서(`sfxr-to-wav` 소스 코드 확인함) 우리가 짤 코드가 거의 없다. 다만 Node.js라는 두 번째 런타임을 미니PC에 얹어야 한다는 점이 "Python이 주력"이라는 전제와 살짝 어긋난다. rfxgen 방식(외부 프로세스 하나만 추가, Python 쪽에서 struct.pack만 새로 짜면 됨)과 비교하면 실질적 이득이 크지 않아서 2순위 후보로만 남겨둔다.
- **Rust 계열(sfxr-rs, rsfxr, usfx)은 전부 탈락.** 유지보수가 다 정체됐거나(2023~2024년 이후 조용함), 있어도 Python 바인딩을 새로 짜야 하고, usfx는 저장소 자체가 사라졌고 라이선스도 AGPL이라 골치 아프다. rfxgen 대비 얻는 게 없다.
- **Faust는 철학적으로는 "코드로 소리를 결정적으로 만든다"는 목표에 잘 맞지만, 이번 목적엔 과하다.** LLVM 기반 컴파일 툴체인 설치가 필요하고, 사운드 하나마다 `.dsp` 코드를 새로 설계해야 해서 sfxr류가 이미 갖춘 "파라미터 24개 슬라이더로 8비트 SFX 뽑기"라는 편의를 처음부터 다시 만드는 셈이다. 미니PC에 무거운 컴파일러를 얹을 이유가 없다.
- **numpy/scipy로 직접 짜는 것은 "재발명"이 아니라 "이식"이라서 리스크가 낮다.** 사용자가 힌트로 준 대로 실제로 진지하게 따져봤다. 밑바탕이 될 알고리즘(rfxgen.h `GenerateWave`)이 이미 공개돼 있고, 짧고(310줄), 의존성이 없고, 라이선스가 허용적이라 그대로 참고해서 옮기면 된다. wav 저장도 Python 표준 라이브러리 `wave` 모듈만으로 충분해서 numpy조차 필수는 아니다(속도가 필요해지면 그때 도입). 유일한 비용은 포팅·검증(소리가 원본과 비슷하게 나는지 확인) 작업 자체이며, 이건 코드 작성 단계라 이번 조사 범위 밖이다.

## 3. 최종 추천 상세 근거

1. **즉시 자동화**: rfxgen CLI가 이미 완성돼 있고 `.rfx` 포맷도 완전히 밝혀졌으니, Python에서 할 일은 파라미터 dict → `struct.pack`으로 104바이트 파일 쓰기, 그리고 `subprocess.run(["rfxgen", "--input", ..., "--output", ...])` 호출뿐이다. GUI를 띄울 필요가 전혀 없다.
2. **유지보수 리스크가 pyfxr보다 낮다**: rfxgen은 2026-08-13까지도 커밋이 있는 활발한 프로젝트이고, 공식 zlib 라이선스라 문제가 생겨도 포크가 자유롭다. pyfxr은 이미 13개월 조용했고, Cython 코어라 새 Python 버전마다 wheel이 안 나오면 컴파일러가 필요해진다.
3. **"유지보수가 완전히 끊겨도 괜찮다"는 근거를 실제로 확인했다**: `rfxgen.h`가 라이브러리 의존성 0인 순수 C 헤더라는 걸 직접 읽었다. 이게 있는 한, rfxgen 프로젝트가 통째로 사라져도 이 짧은 알고리즘 하나를 Python으로 옮기면 그만이다. 사용자가 처음에 짐작한 "포크가 가능하고 소리 합성 코드는 잘 안 바뀐다"는 전제가 소스 코드 레벨에서 사실로 확인됐다.
4. **파라미터 세밀도는 pyfxr과 동일**: 어차피 같은 sfxr 계열 24개 필드(엔벨로프·주파수 슬라이드·비브라토·아르페지오·듀티스윕·페이저·LPF/HPF)라서, rfxgen으로 바꾼다고 표현력을 잃는 게 없다.

---

## 4. 아직 확인 못한 것 / 사용자에게 물어볼 것

1. **지금 바로 "rfxgen 서브프로세스 방식"으로 구현을 시작할지, 아니면 처음부터 "Python 포팅" 방식으로 갈지** 확인 필요. 전자는 당장 코드량이 적고 빠르지만 외부 실행파일 하나를 프로젝트에 들고 다녀야 한다. 후자는 초기 포팅·검증 공수가 들지만 외부 의존이 완전히 없어진다. 이번 조사는 두 방식이 모두 실현 가능하다는 것까지만 확인했고, 둘 중 뭘 먼저 할지는 결정하지 않았다.
2. **`.rfx`의 엔디안**을 소스 코드 주석에서 명문화된 근거로 못 찾았다(x64 전제로는 리틀 엔디안이 사실상 확실하지만, 실물 파일을 만들어 rfxgen에 먹여보는 검증은 아직 안 했다).
3. **jsfxr(`sfxr-to-wav`)의 Node.js 의존을 받아들일지**도 물어보지 않았다. 구현 공수가 제일 적은 방식이라 후보로는 남겨둔다.
4. rfxgen 실행 파일을 프로젝트 저장소에 커밋해서 들고 다닐지, 아니면 빌드/설치 스크립트로 매번 받아올지 같은 **배치 방식**은 이번 조사 범위 밖이라 안 정했다.
